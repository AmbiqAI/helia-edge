title: Export and quantization
description: Export a TensorFlow-backed Keras model to LiteRT with helia_edge.export, inspect predictions and save the model artifact.

`helia_edge.export` converts a Keras model to LiteRT and returns the bytes with their identity. Conversion uses TensorFlow even when another part of your project uses the Torch backend. Run it in the appropriate environment and check the operators and input contract required by your deployment target.

## Install the conversion capability

From the source checkout used by the installation guide:

```sh
uv sync --python 3.12 --extra litert
```

Use a TensorFlow-backed Keras model. See [Backend support](/helia-edge/getting-started/backends/) for the supported Python environment.

## Export and inspect

`export_model` takes an `ExportSpec` that states every setting that changes the exported bytes. With a trained `model` and a NumPy array `representative_x` matching its input shape:

```python
from pathlib import Path

import numpy as np
from helia_edge.export import ExportSpec, LiteRTRunner, export_model

spec = ExportSpec(precision="a8w8", io_dtype="int8", mode="concrete")
result = export_model(model, spec, calibration=representative_x.astype(np.float32))
print(result.sha256, result.inputs[0].scale, result.environment.helia_edge)
predictions = LiteRTRunner(result.content).predict(representative_x)
Path("model.tflite").write_bytes(result.content)
```

| Precision | Graph | Input/output dtype |
|---|---|---|
| `fp32` | float32 weights and compute | `float32` |
| `fp32-w16` | float16 weights, dequantized at runtime; float32 compute | `float32` |
| `fp16` | native float16 graph | `float16` |
| `a8w8` | int8 activations and weights | `int8` or `float32` |
| `a16w8` | int16 activations, int8 weights | `int16` or `float32` |

- `mode` and `io_dtype` have no defaults, and an invalid precision/dtype pair is rejected.
- `a8w8` and `a16w8` need calibration: a non-empty, finite float32 array shaped like the model input, used one sample at a time in stored order. Other precisions refuse calibration data.
- Export needs a backend with an exporter for the format; the built-in `litert` exporter needs the TensorFlow backend. A model with several inputs takes calibration as a mapping of input name to samples and the `keras` or `saved_model` mode (see [Streaming models](#streaming-models)). A model trained with the Torch backend is rebuilt from its params and weights in a process started with `KERAS_BACKEND=tensorflow`.
- Choose representative inputs from the distribution the model will encounter. Compare predictions against the original model and evaluate task quality on held-out data before deployment.
- `ExportSpec` values match helia-benchmark's precision names.
- `LiteRTRunner` runs model bytes with ai-edge-litert, rounding and saturating integer inputs. It runs native float16 graphs where the runtime has float16 kernels for every operator.

## Streaming models

A streaming model processes one step per call and carries its recurrent state as explicit inputs and outputs. Name each state pair with `state_input(k, ...)` and `state_output(k, ...)`: the runtime feeds `state_out_k` back as `state_in_k` and feeds zeros at the start of an independent sequence. `StreamingLSTMCell` is one LSTM step with the weight layout of `keras.layers.LSTMCell`.

```python
import keras
import numpy as np
from helia_edge.export import ExportSpec, LiteRTStreamRunner, export_model, stream_calibration
from helia_edge.layers import StreamingLSTMCell, state_input, state_output

keras.utils.set_random_seed(0)
x = keras.Input((16,), batch_size=1, name="features")
h, c = state_input(0, (32,), batch_size=1), state_input(1, (32,), batch_size=1)
h_next, c_next = StreamingLSTMCell(32)([x, h, c])
prob = keras.layers.Dense(1, activation="sigmoid", name="prob")(h_next)
model = keras.Model([x, h, c], [prob, state_output(0, h_next), state_output(1, c_next)])

features = np.random.default_rng(0).normal(size=(200, 16)).astype(np.float32)
calibration = stream_calibration(model, {"features": features})
result = export_model(model, ExportSpec(precision="a16w8", io_dtype="int16", mode="keras"), calibration)
runner = LiteRTStreamRunner(result.content)
fed, outputs = runner.run({"features": runner.encode("features", features[:50, None])})
probabilities = runner.decode("prob", outputs["prob"])
```

- **Mode:** use `keras` or `saved_model`. `concrete` converts single-input models only, because its graph has no signature to name inputs and states.
- **Records:** `result.inputs` and `result.outputs` list tensors in the model's subgraph order. State tensors have role `state` and the index `pair` of their pair; the converter may reorder inputs, so address them by name.
- **Calibration:** `stream_calibration` runs the Keras model over the signal inputs and returns every input, the state inputs filled with the states the model produces (zero at the start and at the steps in `resets`).
- **Tied state:** with integer I/O (`a8w8` with `int8`, `a16w8` with `int16`), the converter calibrates `state_in_k` and `state_out_k` separately. Export then gives each pair one scale and zero point whose range covers both tensors' ranges (for `int16`, the larger scale), so a raw `state_out_k` keeps its value as the next `state_in_k`; the bias of a fully connected or convolution layer that reads a state is requantized with it. It refuses when the tied scale differs from either original by more than `ExportSpec.state_tie_tolerance` of it (default 1%, at most 50%), or when an operator that needs the state tensor's parameters unchanged (such as a concatenation, or a tanh writing the state) reads or writes it; a reshape passes the tied parameters on to its output. State inputs and outputs must pair up with equal shapes and types, and every output needs its own name (two outputs of one layer share it). The manifest records `state_scales_tied`.
- **Running:** `LiteRTStreamRunner` runs a stream on raw tensors, carrying the state unchanged; it returns every input as fed and every output, stacked by step. `LiteRTRunner` stays single-input.
- Export recipes take streaming models with one signal input; see [Export recipes](#export-recipes-and-the-command-line).

## Lowerings

Some models are built from operators an accelerator does not run, or that integer kernels cannot quantize. A lowering rebuilds such a model, with its weights, from operators that do, keeping its input and output names and state pairs. Set `ExportSpec.lowering` to its name and pass the architecture the model was built as:

```python
spec = ExportSpec(precision="a16w8", io_dtype="int16", mode="keras", lowering="npu")
result = export_model(model, spec, calibration, architecture="vad_silero_v6")
```

- **Lookup:** the lowering is `helia_edge.registry.lowerings["<architecture>:<lowering>"]`. Without `architecture` the export is refused; an unregistered key raises `NotRegistered`.
- **Built in:** `vad_silero_v6:npu`, Silero VAD v6 for an Ethos-U NPU, which quantizes to `a16w8` with the default `strict: true` (see [Import weights](/helia-edge/guide/import-weights/)).
- **Calibration:** the samples are fed to the lowered model; for a streaming model, `stream_calibration` with the model as built gives the states.

## Export recipes and the command line

An export recipe (`schema: helia-edge/export@1`) states the model source, calibration and reference data, and every export. Every file it names carries a sha256:

```yaml
schema: helia-edge/export@1
model: {kind: params_seed, architecture: mlperf_tiny, params: {architecture: ad}, seed: 20260929}
calibration:
  source: {kind: array, file: {kind: path, path: calibration.npy, sha256: <sha256>}}
  samples: 256
reference:
  source: {kind: array, file: {kind: url, url: https://example.com/reference.npz, sha256: <sha256>}, key: x}
exports:
  - {name: fp32, precision: fp32, io_dtype: float32, mode: concrete}
  - {name: a8w8, precision: a8w8, io_dtype: int8, mode: concrete}
```

```sh
KERAS_BACKEND=tensorflow helia-edge export run recipe.yaml --out exports
helia-edge export verify exports/manifest.json
```

- **Model kinds:**
  - `params_seed`: an architecture from `BUILTIN_ARCHITECTURES` (`tcn`, `mlperf_tiny`, `miniresnet_v1`, `timeppg`, `cornet`, `vad_silero_v6`), built from params with a seeded initialization;
  - `params_weights`: the same architectures, with trained weights loaded;
  - `params_import`: the same architectures, with weights imported from a file trained elsewhere through a named mapping in `helia_edge.registry.weight_mappings` (see [Import weights](/helia-edge/guide/import-weights/)); the file's sha256 must be the one the mapping is pinned to;
  - `keras_file`: a saved `.keras` model;
  - `tflite_import`: an existing `.tflite` file, taken as is.
- **Lowerings:** an export's `lowering` applies to `params_seed`, `params_weights` and `params_import` models, with their `architecture`; a `keras_file` recipe with a lowering is refused. The manifest records it in the entry's spec.
- **Sources:** `path` sources resolve relative to the recipe. `url` sources are downloaded once into `~/.cache/helia-edge/sources` (set `HELIA_EDGE_CACHE` to move it). A source whose sha256 differs is refused.
- **Calibration and reference data:** calibration uses the first `samples` rows in stored order (more rows than stored is an error). Reference inputs are run with LiteRT's reference kernels; the inputs as fed and the outputs are saved as `.npy` files next to each model.
- **Streaming models:** for a model with state pairs and one signal input, calibration and reference rows are consecutive calls of the signal input.
  - Calibration feeds the states the model produces (`stream_calibration`), zero at the start and at the steps in `resets`.
  - The reference becomes a `helia-model-zoo/golden@2` sequence golden (`reference/golden.npz`): `input_i`/`output_i` in subgraph order, raw values stacked by step, each `state_out_k` carried into the next `state_in_k` and reset at `resets` (steps after 0).
  - The manifest's `reference.golden` records its file, steps, resets and source; the model zoo's `golden.check` validates it.
- **Batch size and session:** models are exported with batch size 1. Each is built in a fresh Keras session, because auto-generated layer names become tensor names in the exported bytes.
- **Manifest:** `manifest.json` (`schema: helia-edge/manifest@1`) records the recipe's sha256, the environment (helia-edge version, plus its commit when installed from a git URL; Python; platform; NumPy, Keras, TensorFlow and ai-edge-litert versions), and each file's sha256. `run` writes into `--out` without removing files from earlier runs; only the entries in the manifest are verified. `helia-edge export schema --kind recipe|manifest` prints the JSON Schemas.
- **`export verify`:** checks in this order:
  - Exit 1 (drift): a file, a source or the recipe changed. Environment differences are still listed.
  - Exit 2 (environment mismatch): the environment differs from the recorded one; nothing is regenerated. `--allow-env-mismatch` regenerates anyway and lists the differences.
  - Otherwise it regenerates every entry and exits 1 if any file's sha256 or size, spec or tensor record differs, and 0 when all match.
  - Exit 3: the manifest is missing or invalid.

## Add an exporter or architecture

`helia_edge.registry` holds the exporters (keyed `"<format>:<backend>"`), the architectures that recipes build, and the [lowerings](#lowerings) (keyed `"<architecture>:<lowering>"`). An exporter is called as `exporter(model, spec, calibration)` and may receive a model with several inputs, with `calibration` a mapping of input name to samples; an exporter that supports single-input models only should refuse others with a `ValueError`. Built-in entries are `"module:attr"` strings, imported only when used. Another package adds entries through the `helia_edge.plugins` entry-point group, without changes to heliaEDGE:

```toml
# pyproject.toml of your package
[project.entry-points."helia_edge.plugins"]
mypkg = "mypkg.edge:register"
```

```python
# mypkg/edge.py
def register(registry):
    registry.architectures.add("my_tcn", "mypkg.models:build_my_tcn")
    registry.exporters.add("litert:torch", "mypkg.export:export_torch_litert")
```

- **Architecture builders** take `(params, input_shape, num_classes)` and return a Keras model with batch size 1.
- **Exporters** take `(model, spec, calibration)` and return an `ExportResult`.
- **Lowerings** take the model as built and return a new model with the same input and output names and state pairs, leaving the original unchanged.
- **Loading:** plugins load once, the first time a key is not found, for example an exporter for a format on the active backend. A plugin that fails does not stop the others; the failures are raised together as `PluginError`. An unknown key raises `NotRegistered`, a `ValueError` that lists what is registered.
- **Recipes:** they export the `litert` format only, because they write and inspect `.tflite` files. Exporters for other formats are used through `export_model`.

## Legacy converters (deprecated)

`TfLiteKerasConverter`, `LiteRTKerasConverter` and `TfLiteKerasInterpreter` still work but emit a `DeprecationWarning`. They produce the same bytes as `export_model` for the same settings. Move to `export_model` and `LiteRTRunner`:

| Legacy | Replacement |
|---|---|
| `LiteRTKerasConverter(model).convert(x, quantization=QuantizationType.INT8, mode=ConversionType.CONCRETE)` | `export_model(model, ExportSpec(precision="a8w8", io_dtype="int8", mode="concrete"), calibration=x.astype(np.float32))` |
| `QuantizationType.FP32`, `FP16`, `FP16_NATIVE`, `INT8`, `INT16X8` | `fp32`, `fp32-w16`, `fp16`, `a8w8`, `a16w8` (`LEGACY_PRECISION` maps them) |
| `converter.predict(x)`, `TfLiteKerasInterpreter(...).predict(x)` | `LiteRTRunner(result.content).predict(x)` |
| `converter.export(path)` | `Path(path).write_bytes(result.content)` |
| `converter.export_header(header_path)` | write the bytes to `path`, then `helia_edge.converters.cpp.xxd_c_dump(path, header_path, var_name="model", chunk_len=20, is_header=True)` |

`ExportSpec` has no defaults for `mode` and `io_dtype`. The legacy converters defaulted to `keras` mode and, without `io_type`, to int8 I/O for `INT8` and float32 I/O for every other precision except `FP16_NATIVE` (float16). For the same bytes, `INT16X8` therefore maps to `a16w8` with `io_dtype="float32"`.

## Hand off to an Ambiq deployment

The exported model is one part of the deployment. Select the inference runtime and check its operator and precision support before integrating it into firmware. Training backend support does not imply that every model can run on every target.

| Keep with the model | Why the deployment needs it |
|---|---|
| Input shape, layout and dtype | Defines how firmware supplies each inference window. |
| Preprocessing parameters | Keeps scaling, filtering and feature extraction consistent with training. |
| Output names and interpretation | Defines class order, thresholds or reconstruction units. |
| Calibration and quantization settings | Explains how the converted artifact was produced. |
| Representative inputs and expected outputs | Enables comparison between host inference and the deployed runtime. |
| Model and source revisions | Identifies the exact artifact being evaluated. |

Validate task quality after conversion, then measure latency and memory with the model on your intended Ambiq board. Host conversion and operation counts do not establish device performance. For streaming models, include the state shapes, initialization and update order described in the model's guide.
